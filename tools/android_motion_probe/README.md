# Native motion load probe

`android-motion-probe.yml` is a diagnostic that runs on explicit dispatch or changes to its own capture tooling. It builds one normal **profile** `lib/main.dart` APK at the checked-out SHA and uses the same APK and pinned 90-second Bee file on an API 35 Pixel 6 and Pixel Tablet. It does not exercise a Together Session or establish physical-device performance.

Phase A plays the same local clip on both AVDs while two native screen recorders run. Phase B keeps the tablet app and emulator alive, stops only the verified task-owned phone AVD after its recording is finalized, seeks the tablet back to the same clip interval and repeats the native recording. Both tablet recordings use 960×600, 3 Mbps, 30 seconds, two guest cores and SwiftShader. The launcher retains the existing 720×1600 phone and 1280×800 tablet framebuffers; this probe does not lower display or capture resolution relative to the prior Profile run.

The artifact keeps the APK, fixture and observer digests; original screenshots; both original AVD videos; device start/stop uptime; raw per-frame PTS; full-decode result; SHA-256 matched device/pulled files; and 1 Hz host `/proc` and cgroup samples for both phases. `result.json` reports diagnostic status and per-phase results. A failed phase leaves its original or partial MP4 and error receipts where available. The upload deliberately excludes the reviewed Bee media file and the generated APK; their digests and build target are retained. No video is interpolated or presented as 30 fps evidence.

Review the tablet's longest original complete-frame gap and moving-picture changes in the targeted Bee interval for A and B. The two Play taps, native observations, screenshots and recorder starts are sequential, so the recordings are not guaranteed to show identical source frames. Device uptime bounds each capture, and original video PTS gives the frame spacing within it; neither establishes exact cross-device source-frame alignment. Align the bounded windows with host CPU pressure, throttling, memory and per-emulator CPU/RSS. A better B than A supports shared-host load as a factor; unchanged poor B redirects investigation to the single-device decoder, compositor, application or recorder path. This probe cannot by itself isolate all those components or approve the final Together demo film.
